## 1. 规则

- 评审对象必须是**冻结版本**：工程版本号、git commit/tag、导出物路径，三者缺一不可。
- **写的人不评审自己的产出。** AI 提交评审包；Claude B 预审；工程师朋友终审。
- 预审发现项必须逐条回应：修复，或书面说明不修的理由并由终审确认。
- 阻塞项未关闭，不得过门；「有条件通过」的条件必须有责任人、截止日期、验证方式。
- 口头结论无效。结论写入本文件并 git commit 后才算生效。
- 评审 ID 规则：`RV-SCH-nnn`（原理图）、`RV-BOM-nnn`（BOM）、`RV-PCB-nnn`（布局）。

## 2. 角色与流程

```
AI 提交评审包
```

## 3. 严重度与结论

### 3.1 发现项严重度

| 严重度 | 定义 | 处理要求 |
|---|---|---|
| **阻塞（Blocker）** | 会导致功能失效、安全问题、无法制造或违反 MUST 需求 | 必须修复并复验，未关闭不得过门 |
| **重要（Major）** | 可能导致性能下降、可靠性风险或返工 | 修复，或有书面理由并经终审接受 |
| **建议（Minor）** | 可读性、优化、未来改进 | 记录，可延后 |

### 3.2 评审结论

| 结论 | 含义 | 后续 |
|---|---|---|
| **通过** | 无阻塞项，重要项已处理或接受 | 过门 |
| **有条件通过** | 无未关闭阻塞项，但附条件 | 条件关闭并复验后过门 |
| **驳回** | 存在阻塞项或设计不可接受 | 修订后重新评审 |
